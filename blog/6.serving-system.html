Building a University LLM Serving System

2026-06-11 · FTU Labs · 12 min read

Four months ago we wrote about turning 88 laptops into a Docker Swarm LLM cluster. That system worked — 40 CPU nodes running a 4B model, an Nvidia Xavier running 35B, all behind nginx. But it was a flat architecture: every request got the same model, every user got the same experience, and there was no way to customize the system for specific academic disciplines.

We’ve been rebuilding. The goal is a proper LLM serving system for a university — one where a law student gets domain-tuned responses backed by legal RAG, a finance student gets quantitative analysis with the right LoRA adapter loaded, and a first-year just chatting about homework gets a fast response from a CPU node without burning GPU cycles.

This is ongoing work. Some pieces are in production, some are being built. This post covers the architecture and what we’ve shipped so far.

What Changed Since the Swarm Post

The original cluster was 40 CPU nodes behind nginx with equal weighting. Here’s what’s different now:

Aspect February 2026 June 2026
Nodes 40 CPU + 1 Xavier 40 CPU + 1 Xavier + 4×V100
CPU model Qwen 4B Q4_K_M Qwen 4B MTP-UD Q4_K_XL + speculative decoding
Routing nginx round-robin Semantic router (complexity-based tier assignment)
Throughput (80 users) ~330 t/s aggregate ~396 t/s aggregate (CPU only, higher with GPU tiers)
Skills None 13 presets + 134-skill library
Auth Open LAN access Google OAuth (ftu.edu.vn domain)

The CPU nodes got a meaningful upgrade: switching from plain Q4_K_M to MTP-UD Q4_K_XL with speculative decoding (ngram-mod + draft-MTP) improved single-node throughput. Combined with flash attention and q4_0 KV cache quantization, each node now runs 4 parallel slots within its 16 GB RAM budget. At 80 concurrent users across 40 nodes, the cluster sustains 396 tokens/second with zero failures.

The Semantic Router

The router is the core of the new architecture. It runs as an inlet filter inside Open WebUI — a Python function that intercepts every chat completion request before it hits a backend. The filter scores each message for complexity and routes it to the appropriate tier.

How it scores

The scoring is intentionally simple — no ML model, no embeddings, just pattern matching that runs in microseconds: 

def score_complexity(messages):
    last_msg = messages[-1]["content"]
    word_count = len(last_msg.split())
    score = 0

    # Length signals complexity
    if word_count > 100:
        score += 40
    elif word_count > 50:
        score += 20

    # Pattern matching for complex tasks
    complex_patterns = [
        "explain", "analyze", "implement", "algorithm",
        "machine learning", "security", "architecture",
        "compare", "evaluate", "design"
    ]
    for pattern in complex_patterns:
        if pattern in last_msg.lower():
            score += 10

    # Penalize simple interactions
    simple_patterns = ["hi", "hello", "thanks", "ok"]
    if last_msg.strip().lower() in simple_patterns:
        score -= 50

    # Conversation depth adds weight
    score += len(messages) * 2

    return score

Tier assignment

Score Tier Backend Model
< 20 Tier 3 CPU pool (40 nodes) Qwen 4B
20–49 Tier 2 Xavier AGX Qwen 35B
≥ 50 Tier 1 V100 cluster REAP-28B

Sticky sessions

Once a conversation is assigned to a tier, it stays there. The router tracks conversation IDs with a 30-minute TTL. This serves two purposes:

  • KV cache coherence — moving a conversation to a different backend means rebuilding the KV cache from scratch. On the V100 with a 28B model, that’s seconds of wasted prefill.
  • Escalation only — conversations can move up to a more powerful tier (if a simple chat turns into a complex request), but never down. This prevents quality degradation mid-conversation.

The router also health-checks each GPU tier. If the V100 node is down, Tier 1 requests fall back to Xavier. If Xavier is down, everything goes to the CPU pool. The CPU pool is always available — 40 nodes make it effectively indestructible.

Skills and Domain Specialization

Raw model access isn’t enough for a university. A student writing a thesis needs different capabilities than one debugging Python homework. We handle this through Open WebUI model presets — specialized system prompts that wrap the base model with domain expertise.

We currently deploy 13 presets:

  • Scientific Writer — IMRAD structure, citation styles (APA, AMA, Vancouver), CONSORT/STROBE/PRISMA reporting guidelines
  • Literature Reviewer — PICO framework, multi-database search strategy, PRISMA synthesis
  • Statistical Analyst — test selection, assumption checking, APA-formatted results
  • Data Explorer — EDA on uploaded files
  • Peer Reviewer — structured manuscript review with severity ratings
  • Grant Writer — proposals targeting NSF, NIH, DOE, DARPA formats
  • ML Engineer — scikit-learn pipelines, model selection, evaluation
  • Market Researcher — consulting-style reports with TAM/SAM/SOM analysis
  • What-If Analyst — scenario modeling and sensitivity analysis
  • Plus: Hypothesis Generator, Data Visualizer, Citation Manager, Diagram Writer

Behind these presets sits a skill library of 134 specialized skills, indexed by keyword. When a user selects a preset, the system loads the relevant skills covering domains from bioinformatics and drug discovery to finance, geospatial analysis, and quantum computing.

All presets are deployed programmatically via a script that writes directly to Open WebUI’s SQLite database — no manual UI clicking required. This makes the skill set version-controlled and reproducible.

Multi-LoRA Serving (In Progress)

Skills and system prompts go far, but they have limits. A system prompt can tell the model how to behave, but it can’t teach it domain knowledge it never learned during pre-training. For that, we need fine-tuning — and for a university serving multiple departments, we need to serve many fine-tuned variants from a single base model.

This is where multi-LoRA serving comes in. The idea, well-described in AWS’s multi-LoRA post, is straightforward:

  1. Keep the base model weights frozen on the GPU — one copy, shared across all requests.
  2. Store LoRA adapters (small low-rank matrices, typically 10–50 MB each) in a library.
  3. At inference time, inject the relevant adapter per-request — a law query activates the law LoRA, a finance query activates the finance LoRA.
  4. The adapter swap happens at the kernel level with near-zero overhead — no model reloading, no GPU memory duplication.

For MoE models like our Qwen variants, vLLM provides a fused_moe_lora kernel that integrates LoRA operations into the expert routing kernel itself — handling both the MoE sparsity and the adapter selection in a single pass.

Our plan

We’re building toward a LoRA library with adapters for specific FTU departments:

Adapter Training Data Use Case
law-vn Vietnamese legal codes, court decisions Legal document analysis, case lookup
finance-quant Financial reports, quantitative analysis papers Portfolio analysis, risk modeling
accounting-vn Vietnamese accounting standards (VAS), tax regulations Financial statement preparation, audit support
trade-intl International trade law, customs procedures Trade compliance, Incoterms analysis
academic-writing Published papers, thesis examples Research writing, citation formatting

The semantic router will be extended to detect domain context and attach the appropriate lora_adapter parameter to the request before it reaches vLLM. Combined with RAG (retrieval over department-specific document stores), this gives each department a model that both knows their domain and can retrieve current documents.

Training-as-a-Service (Planned)

The second user-facing surface is more ambitious: let users train their own models.

The inspiration comes from services like Hugging Face AutoTrain and Thinking Machines’ Tinker — platforms that abstract away the complexity of fine-tuning and let users focus on their data and evaluation criteria.

We’re starting with 4B models only. At this size, a LoRA fine-tune on the H100 takes minutes, not hours — fast enough for an interactive workflow where a researcher can iterate on their training data and see results quickly.

Why LoRA, not full fine-tuning

Three practical reasons:

  • Storage — a full 4B model checkpoint is ~8 GB. A LoRA adapter is 10–50 MB. With dozens of department-specific variants, the difference between storing full models vs. adapters is 100×.
  • Serving efficiency — one base model in GPU memory, adapters swapped per-request. Full fine-tunes would require loading separate model instances, which doesn’t scale on our hardware.
  • Composability — LoRA adapters can theoretically be merged or stacked. A student in international business law could benefit from both the law-vn and trade-intl adapters.

The hot-swap pipeline

Once a LoRA adapter is trained and evaluated, deploying it should be instant. vLLM supports --enable-lora with a configurable adapter directory — new adapters placed in the directory become available for the next request without restarting the server. The serving layer maps adapter names to request parameters: 

# Adapter selection in the semantic router
if domain == "law" and lang == "vi":
    request["model"] = "qwen-4b"  # base model
    request["lora_adapter"] = "law-vn"
elif domain == "finance":
    request["model"] = "qwen-4b"
    request["lora_adapter"] = "finance-quant"
else:
    request["model"] = "qwen-4b"  # no adapter, base model only

This integrates with the existing semantic router — the same filter that picks the tier (CPU/Xavier/V100) also picks the LoRA adapter based on conversation context.

The CPU tier is deceptively strong. Individually each i7 node is slow (~10 t/s), but 40 of them in parallel handle the bulk of university traffic — most interactions are simple questions that a 4B model handles perfectly well. The semantic router ensures GPU resources are reserved for requests that actually need them.

Monitoring

Every node runs Prometheus node-exporter. Grafana dashboards show per-node CPU, memory, and GPU utilization in real time. LiteLLM provides a second routing layer with latency-based request distribution across all 43 backends, with automatic cooldown (60s) for nodes that fail 3 consecutive requests.

The monitoring stack answers the questions that matter in production:

  • Which nodes are overloaded? (CPU % > 90% sustained)
  • Is the NFS model store a bottleneck? (read latency on /opt/cluster/models)
  • Are GPU tiers healthy? (semantic router health probes)
  • What’s the actual tier distribution? (% requests hitting CPU vs Xavier vs V100)

Why Not Just Use an API?

The obvious question: why build all this when you can just call OpenAI or Claude?

  • Cost at scale — a university with thousands of students burning API tokens gets expensive fast. Our marginal cost per query is electricity.
  • Data sovereignty — student conversations, research data, and department documents stay on campus infrastructure. No data leaves the network.
  • Customization — you can’t fine-tune GPT-4 on your legal corpus. You can fine-tune a 4B model on our H100 and deploy it in minutes.
  • Education — the system is the curriculum. Students learn distributed systems, GPU programming, and ML ops by building and operating the infrastructure they use every day.
